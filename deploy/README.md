# deploy

The Compose stack for the Otomo services, plus the scripts that bring it up,
provision it and release into it.

COM-7 is the file that matters: `compose.yaml`, whose acceptance criterion is
`"docker compose up" brings up infrastructure cleanly on a fresh VM`
(`design/00-common-stack.md:172`). Read `compose.yaml` first; its header comments
carry the three decisions below in the place a person changing it will see them.

```
deploy/
  compose.yaml                    the stack: COM-7
  compose.smoke.yaml              2 s access tokens, for smoke-player-login.sh only
  .env.example                    every variable, no secrets; see COM-9
  postgres/init/01-provision.sh   COM-6: databases, roles, and who may connect
  valkey/valkey.conf.example      tracked template; valkey.conf is rendered and ignored
  scripts/generate-secrets.sh     .env, the Valkey config, the secrets directories and root password
  scripts/up.sh                   the one command to bring the stack up
  scripts/rotate-root-password.sh write a new root password and rotate it in the database
  scripts/provision-upgrade.sh    re-run provisioning on a host whose data dir exists
  scripts/test-provision.sh       throwaway-cluster check of the provisioning script
  scripts/test-generate-secrets.sh throwaway-dir check of generate-secrets.sh
  scripts/check-compose.sh        CI check of the properties of the rendered compose file
  scripts/smoke-player-login.sh   end-to-end player login through the player edge
  scripts/release.sh              build, tag with a git SHA, push, deploy, probe
  scripts/tunnel.sh               SSH local forward to gateway_dev
  scripts/lib.sh                  the probes, sourced by the two above
  docs/ADMIN-ACCESS.md            reaching and using the admin plane
  observability/prometheus.yml    scrape jobs for every service and exporter
  observability/loki.yml          Loki single-binary, filesystem storage, 72h retention
  observability/config.alloy      Docker log discovery, JSON level, push to Loki
  secrets/                        generated at deploy time; never in the repository
  secrets/admin_auth/             admin-auth's signing key, TOTP key and root password
```

## Quick start

Requirements: Docker with the Compose plugin, `openssl`, and `git`. Nothing else -
no Go, no Node, no Postgres client.

```sh
git clone https://github.com/otomo-live/otomo.git
cd otomo
deploy/scripts/generate-secrets.sh   # writes deploy/.env and deploy/valkey/valkey.conf
deploy/scripts/up.sh                 # builds, starts, migrates, generates the signing key, probes
```

`up.sh` is `docker compose up` plus the two things YAML cannot express: a set of
passwords, and an auth signing key that has to be generated by the auth binary
against a migrated database. Once `generate-secrets.sh` has run, a plain
`docker compose --env-file deploy/.env -f deploy/compose.yaml up -d` from the
repository root is the same stack; `up.sh` exists so that the first run does not
depend on knowing the order.

### Player login, end to end

Once `up.sh` has run once, this checks a player login through the player edge:
`POST /auth/anonymous`, then `GET /api/player/session/me` with the token (a `501`
from Session is the pass: both the gateway's and Session's token guards accepted
it), then an expired token → `401 expired` → `POST /auth/refresh` → retry, refresh
reuse and logout:

```sh
deploy/scripts/smoke-player-login.sh
```

It needs `curl` and `python3` on the host. It rebuilds and restarts `auth`, `session`
and `gateway` with `compose.smoke.yaml` (2 s access tokens, so the expiry case takes
about 35 s instead of 15 minutes), prints one line per check, exits non-zero on any
failure, and on exit recreates `auth` with its normal 15-minute tokens.

`scripts/check-compose.sh` pins the player issuer, audience and JWKS URL across
`compose.yaml` and every `services/*/.env.example`, so they cannot drift apart
without failing that check.

What comes up, and what it publishes:

| Service | Published | Reachable at |
|---|---|---|
| `gateway` | `${GATEWAY_BIND_ADDR:-127.0.0.1}:${GATEWAY_PORT:-8080}` | the player edge; loopback unless `GATEWAY_BIND_ADDR` publishes it (Docker ports bypass ufw) |
| `gateway_dev` | `127.0.0.1:${GATEWAY_DEV_PORT:-8090}` | the staff control plane, loopback only |
| `registry` | `127.0.0.1:5000` | the release store, loopback only |
| `postgres`, `valkey`, `auth`, `session` | nothing | `otomo-net`, by service name |
| `admin-auth`, `config`, `patch`, `dashboard` | nothing | `otomo-net`, by service name |
| `admin-ui` | nothing | `gateway_dev` at `/admin/` |

### The admin plane

The admin plane adds the services behind `gateway_dev`. Each one-shot migration runs
before the services that depend on it, and none publishes a host port:

| Service | Image | Starts after | Notes |
|---|---|---|---|
| `admin-auth-migrate` | `otomo-admin_auth` | Postgres healthy | one-shot `migrate`, `restart: "no"` |
| `admin-auth` | `otomo-admin_auth` | `admin-auth-migrate` completes | staff identity provider; serves the JWKS every verifier fetches |
| `config-migrate` | `otomo-config` | Postgres healthy | one-shot `migrate`, `restart: "no"` |
| `config` | `otomo-config` | `config-migrate` completes | owns the `config` database and the read-write `blobs` volume |
| `patch` | `otomo-patch` | `config-migrate` completes | reads `config` as `patch_ro`; mounts `blobs` read-only |
| `dashboard` | `otomo-dashboard` | `admin-auth` starts | Prometheus/Loki URLs point at the observability stack; it degrades without them |
| `admin-ui` | `otomo-adminui` | — | nginx serving the staff SPA at `/admin/` on `:8080` |

Every staff verifier (`gateway`, `gateway_dev`, `config`, `patch`, `dashboard`)
pins `http://admin-auth:8080/.well-known/jwks.json` and issuer
`https://admin-auth.otomo.internal` in `compose.yaml`; there is no
`STAFF_JWKS_URL`/`ADMIN_AUTH_URL` override in `deploy/.env` any more.

#### Reaching the admin plane

`gateway_dev` binds only the host's loopback interface, so the staff plane is
reached through an SSH local forward, not by pointing a browser at the host.
`deploy/scripts/tunnel.sh` opens that forward and refuses a local port that is
already in use:

```sh
OTOMO_SSH=you@play.example.com deploy/scripts/tunnel.sh   # then open http://localhost:8090/admin/
```

`docs/ADMIN-ACCESS.md` is the step-by-step guide: prerequisites (Chrome or
Firefox — Safari rejects the `Secure` refresh cookie on `localhost`), the root
break-glass sign-in, inviting and onboarding personal admins, everyday sign-in,
and rotation of the root password. See also "Root account" below.

### The observability stack

The Dashboard is a thin query layer; the stores and collectors it reads run in
this same stack. All of them are on `otomo-net` and **none publishes a port**, so
`docker compose up` brings them up with everything else and they stay off the
internet:

| Service | Image | Limit | What it does | Retention |
|---|---|---|---|---|
| `prometheus` | `prom/prometheus:v3.15.0` | 200 MB | scrapes every service's internal `:9090` `/metrics` every 15s, plus the host/container/Postgres exporters and itself, Loki and Alloy | 7d or 2GB |
| `loki` | `grafana/loki:3.7.8` | 150 MB | log store; filesystem storage on `loki-data` | 72h, enforced by the compactor |
| `alloy` | `grafana/alloy:v1.20.0` | 100 MB | tails this project's container logs, promotes only `service` and lower-case `level`, pushes to Loki | — |
| `node_exporter` | `prom/node-exporter:v1.9.1` | 30 MB | host CPU, memory, disk and network | — |
| `cadvisor` | `gcr.io/cadvisor/cadvisor:v0.52.1` | 80 MB | per-container CPU and memory | — |
| `postgres_exporter` | `quay.io/prometheuscommunity/postgres-exporter:v0.17.1` | 30 MB | Postgres connections, query rates and database size | — |

The limits total 590 MB, under the 650 MB budget `scripts/check-compose.sh`
asserts. Every `service` label Prometheus attaches is the compose service name,
which is the label the Dashboard's PromQL templates select on; every Loki stream
carries only `service` and `level`, matching the Dashboard's LogQL. Services log
JSON with an upper-case `level` (Go `slog`), which Alloy lower-cases and maps
`warning` → `warn`; a non-JSON line keeps `service` and gets no `level`.

Alloy mounts `/var/run/docker.sock:ro`. That socket is **root-equivalent**: a
read-only bind does not restrict the HTTP verbs, so anything that can reach it
can start a privileged container. It is accepted for M1 because Alloy itself
publishes no port and it is the same trust boundary as the deploy account; the
config file repeats this and NET-1 replaces discovery with a socket proxy or a
Swarm-aware collector.

`postgres_exporter` connects as a monitoring-only role added by
`postgres/init/01-provision.sh`: `pg_monitor` plus CONNECT on the `postgres`
database and nothing else. As with the other roles, a host whose data directory
already exists converges it with `scripts/provision-upgrade.sh`; a fresh host gets
it from the init script.

#### Reaching Prometheus and Loki for debugging

Neither store is published. Two ways in, both over SSH:

- **One-off API calls** through a shell in the container (Prometheus's image has
  a shell with `wget`):
  ```sh
  ssh deploy@host
  cd otomo/deploy
  docker compose exec prometheus \
    wget -qO- 'http://localhost:9090/api/v1/query?query=up'
  ```
- **An interactive UI** through a throwaway container that publishes the store on
  the host's loopback, then an SSH local forward:
  ```sh
  # on the host, one per store; 9091 -> Prometheus, 9092 -> Loki
  docker run --rm -d --name prometheus-tunnel \
    --network otomo-net -p 127.0.0.1:9091:9090 \
    alpine/socat tcp-listen:9090,fork tcp-connect:prometheus:9090
  docker run --rm -d --name loki-tunnel \
    --network otomo-net -p 127.0.0.1:9092:3100 \
    alpine/socat tcp-listen:3100,fork tcp-connect:loki:3100

  # on the workstation, then open http://localhost:9091 (or :9092)
  ssh -L 9091:127.0.0.1:9091 -L 9092:127.0.0.1:9092 deploy@host
  ```

  The throwaway ports are bound to `127.0.0.1` only, so this is no more exposed
  than the host's SSH port, and `docker run --rm` removes the forwarder when you
  stop it.

### First run and the secrets it expects

`up.sh` brings the stack up in this order: `.env`, the Valkey config and
`deploy/secrets/admin_auth/` must exist (run `generate-secrets.sh` first), images
build, Postgres/Valkey/registry reach healthy, **all three `*-migrate` one-shots
run**, `auth genkey` writes the player signing key when it is absent, then
`admin_auth genkey -totp`, `admin_auth genkey` and `admin_auth bootstrap-root`
generate admin-auth's keys and create the break-glass root account, and finally
`up -d` starts the rest and readiness is polled on internal `:9090` (admin-ui at
`:8080/admin/`).

The files under `deploy/secrets/admin_auth/`:

| File | Read as | Created by |
|---|---|---|
| `signing_key.pem` | `ADMIN_AUTH_SIGNING_KEY_PATH` | `up.sh` (`admin_auth genkey`; writes the file and its DB row) |
| `totp.key` | `ADMIN_AUTH_TOTP_KEY_PATH` | `up.sh` (`admin_auth genkey -totp`; needs no database) |
| `root_password` | `ADMIN_AUTH_ROOT_PASSWORD_FILE` | `generate-secrets.sh` (0600); read by `up.sh`'s `bootstrap-root` |

`generate-secrets.sh` creates `deploy/secrets/admin_auth/` as 0700 and owned by
the admin-auth container's uid (65532), which has to write the two key files
there. Running as root it chowns the directory itself; otherwise it prints the
exact `sudo chown -R 65532:65532 …` line to run. Because the directory and the
password file then belong to uid 65532, reading `root_password` from the host
needs `sudo`.

Each key is generated only when its file is absent (the binary refuses to
overwrite), and `bootstrap-root` runs on **every** `up` because it is idempotent:
a fresh host gets root and an existing one prints `root already exists`. If
`root_password` is missing, `up.sh` prints the path and stops **before** it starts
`admin-auth`, rather than leaving a container crash-looping on a file that only
appears in its log. `deploy/scripts/generate-secrets.sh` is the fix.

### Root account

Root is a single break-glass account with no MFA, by design (decision D5). Its
only job is creating personal admin accounts; day-to-day work happens in those
accounts, so the password can stay in a host secret that admins read over SSH.

- **Where it lives:** `deploy/secrets/admin_auth/root_password`, mode 0600,
  generated by `deploy/scripts/generate-secrets.sh` and owned by uid 65532.
- **Reading it over SSH:** `sudo cat deploy/secrets/admin_auth/root_password`, or
  as the deploy user when that user is uid 65532. The value is never printed by
  any script and never leaves the host.
- **First sign-in:** reach the staff plane through the SSH tunnel to the loopback
  listener, then open `http://localhost:8090/admin/` and sign in as
  `root@otomo.internal`. Create one personal admin account per person from there.
- **Rotation:** `sudo deploy/scripts/rotate-root-password.sh`. It writes a new
  0600 password, keeps the old one as `root_password.previous` (0600) while
  `bootstrap-root -rotate` runs, and restores it if that fails. `-rotate` also
  revokes every live root session. The new password is read where the old one was.

## Provisioning an existing host

`postgres/init/01-provision.sh` is run by the Postgres image entrypoint only on the
first start with an empty data directory. A host that already has a `postgres-data`
volume never runs it again, so a change to the script (a new database or role, such
as `admin_auth`/`admin_auth_rw` added later) does not reach that host by pulling
a new image or running `up.sh`.

`scripts/provision-upgrade.sh` is for that case. It requires the `postgres` service
to be running, then runs the same file inside the container, reading every
`*_PASSWORD` it needs from `deploy/.env` (never sourcing the file) and passing them
through the container's environment:

```sh
deploy/scripts/up.sh                     # if the stack is not up yet
deploy/scripts/provision-upgrade.sh
```

Run it after changing `postgres/init/01-provision.sh` on a host that was provisioned
before that change. It is idempotent: role and database creation are guarded, and
`REVOKE`/`GRANT` are already idempotent, so running it twice changes nothing. It does
**reset each service role's password to the value in `deploy/.env`**, because that is
what converges a role whose password has changed; if a running service still uses an
old password it is a hard failure, not silent drift, so pair a password change with a
restart of the services that use it.

On a host provisioned before the admin-auth roles existed, `generate-secrets.sh` has to run first (or
again) to add `ADMIN_AUTH_RW_PASSWORD` to the existing `.env`; `provision-upgrade.sh`
refuses to run while any required password is empty.

## Verified on a live host

Run on 2026-09-22 on the VPS this stack was built for (2 vCPU, 3819 MB RAM,
Docker 29.8.1, Compose v5.5.1), which also ran a CI server and a live game server. It is written down because "the compose file parses" and "the stack comes up"
are different claims, and only the second one is COM-7's acceptance criterion.

- **`docker compose up` from a clean state.** `up.sh` ran end to end: `postgres` and
  `valkey` reached healthy, the registry answered `/v2/`, `auth-migrate` applied
  version 1, `genkey` wrote the key and its row, all six containers came up, and the
  probes returned `ok` for auth's `/healthz`, `/readyz` and JWKS and for both
  gateways' `/healthz`.
- **COM-6's isolation holds**, checked by connecting as each role rather than by
  reading the script. `config_rw` reaches `config` and is refused `session` with
  `FATAL: permission denied for database "session"`; `auth_rw` reaches `auth` and is
  refused `config`; `patch_ro` reads `config`.
- **`release.sh` end to end.** It built and pushed `127.0.0.1:5000/otomo-auth:43885e6`,
  wrote the tag into `.env`, recreated `auth-migrate` and `auth`, and reported
  `ok auth (/readyz)`.
- **Both registry paths, not only push.** A retagged copy was pushed, removed from the
  local daemon, and pulled back with the same digest (`sha256:39990e05...`);
  `_catalog` and `tags/list` both answered.
- **External exposure is what the file intends.** From a host outside the VPS: 8080
  answers with an HTTP 404, so it is listening and reachable; 8090 times out (ufw
  drops it, and it is loopback-bound regardless); 5000 refuses the connection because
  it is loopback-bound.
- **The stack idles at about 78 MiB** across six containers (gateway 2.4, auth 2.6,
  gateway_dev 2.2, valkey 3.2, registry 10.2, postgres 57.1 MiB) against roughly
  2400 MB available. Postgres is almost the whole footprint.
- **`/readyz` on both gateways answers 503 in under a second**, which is the designed
  signal. Measured rather than inferred: 18 of 18 probes answered, and 6 probes
  immediately after a gateway restart answered within a second. An earlier report of
  "no response" came from a bug in the probe helper itself, not from the gateways;
  see the commit that fixed `report_http`.

Re-running `up.sh` on the stack it has just created recreates `auth` and `auth-migrate`
and leaves Postgres, Valkey, the registry and both gateways untouched. The recreate is a
brief restart plus a goose run that reports `no migrations to run`, so it is safe, but
it is not a no-op, and COM-8's deploy step should use `release.sh`'s per-service
`up -d` rather than `up.sh`.

Not verified: no second host has been tried, so "on a fresh VM" rests on this one; TLS,
rate limiting and whatever sits in front of the player edge do not exist here; and the
admin plane (admin-auth, config, patch, dashboard, admin-ui) has
not been run on a host yet.

## The three decisions

**1. Nothing publishes a port except the two gateways and the registry, and the
services address each other by Compose DNS.** That is what `design/00-common-stack.md:74`
asks for, and it is what makes NET-1 (a second host, a Swarm overlay) a change to
this one file rather than to any service.

**2. `gateway` and `gateway_dev` publish on deliberately different interfaces.**
`gateway` is the player edge and binds every interface on the one port a host's
firewall already allows. `gateway_dev` is the staff control plane and stays on the
loopback interface, because its own README says it must not be internet-reachable
(`services/gateway_dev/README.md:117`): `/admin-auth/` and `/admin/` are public by
design, since `/admin-auth/*` is how you get a token in the first place. Exposing
that is not a hardening nicety, it is a whole-service bypass. Keeping it on
loopback means a firewall rule is not what stands between the internet and it.

**3. Secrets arrive through `deploy/.env` and two generated files, never through
this repository (COM-9).** `generate-secrets.sh` creates passwords as hex, which is
why they need no escaping in a DSN, in SQL or in a sed substitution. Two
consequences to know rather than discover:

- A Postgres password held in the container's environment is visible to anyone who
  can talk to the Docker daemon (`docker inspect`). That is the COM-9 shape - an env
  file written at deploy time - and it is what NET-1's Swarm secrets replace.
- The Valkey config and the auth signing key are files, not variables, because
  neither service can take them any other way.

## Resource envelope

Measured on the host this was built for (2 vCPU Haswell with one thread per core,
3819 MB RAM, 2 GB swap, 38 GB disk, 27 GB free before this stack existed) while it
also ran Jenkins at ~905 MB, a latency-sensitive game server on UDP, and a stray
`otomo-pg` container:

- **Memory fits, with room.** ~2430 MB was available before the stack; the stack
  idles in the low hundreds of megabytes. `shared_buffers=192MB` and Valkey's
  `maxmemory 192mb` are the two deliberate caps, and both are ceilings rather than
  reservations.
- **CPU is the real constraint, not memory.** Two cores are shared with a live game
  server and with Jenkins, and `go build` plus `go test -race` for three services
  will saturate both. Do not run a release during a busy match; that is a
  scheduling decision, not something this file can enforce.
- **Disk is the second constraint.** The images are the small part. `golang:1.27.1-bookworm`
  is the large one, and BuildKit's cache volumes behind `--mount=type=cache` in the
  Dockerfiles grow with every build. `docker builder prune` reclaims it, and
  nothing here prunes on its own.
- **`postgres:17` runs one instance for every service**, so COM-14's pool sizing has
  one place to be wrong in rather than several. `max_connections=80` is the ceiling
  the sum of the services' pools has to stay under.

## Traps worth having written down

- **`postgres/init/01-provision.sh` runs once**, on the first start with an empty
  data directory, but it is idempotent and can be run against an existing host with
  `scripts/provision-upgrade.sh`. Editing it does not change an existing database on
  its own: either run that script or drop the `postgres-data` volume.
- **The distroless images have no shell**, so no Compose healthcheck can be written
  for `auth`, `gateway` or `gateway_dev`, and `docker compose exec` has nothing to
  exec. Readiness is polled from outside by a throwaway container -
  `scripts/lib.sh` is where that lives - which is also what COM-8's deploy step
  must do.
- **`/healthz` and `/readyz` are on the metrics listener, port 9090**, not on the
  public 8080. The public listener carries routes only.
- **The auth signing key cannot be made with `openssl`.** `auth genkey` inserts the
  public half as a `signing_key` row, and `auth serve` refuses to start when the
  file's key has no active row (`services/auth/auth.go:133`). It also refuses to
  overwrite an existing file, which is why it is a step in `up.sh` and not a
  one-shot service on the Compose dependency chain: a second `up` would fail the
  chain and leave `auth` unable to start.
- **`deploy/secrets/` is mode 1777**, and that is the price of a non-root container
  with no shell in it. The key is written by uid 65532 (distroless `nonroot`) and
  read by the same uid; the image has nothing with which to `chown` a directory, so
  the host directory has to let that uid create a file in it. The sticky bit means
  only the owner can replace the file, and the file itself is 0600. The cost:
  reading the key from the host needs `sudo cat deploy/secrets/auth_signing_key.pem`.
- **`deploy/valkey/valkey.conf` is mode 0644** for the same reason - the Valkey
  image runs as its own non-root user, so a 0600 file is a config file it cannot
  open. The password in it is the one already in `.env` at 0600. On a host with
  other users, tighten it to the image's own uid instead.
- **A 503 from either gateway's `/readyz` means one token domain is not fetching,
  not that the stack is down.** Both gateways wait on two domains; now that
  `admin-auth` is in this stack, the staff half turns green once it answers and its
  JWKS has been fetched. The JWKS client retries in the background
  (`services/gateway/internal/authn/jwks.go:105`), so an admin-auth restart
  degrades readiness instead of crashing a gateway.
- **Images are addressed as `127.0.0.1:5000/...` from the host's own daemon.** Docker
  exempts `127.0.0.0/8` from TLS, so this needs no `insecure-registries` entry; a
  hostname such as `registry:5000` would need one, and adding it means restarting
  dockerd on a host that is running a game server. That is the change NET-1 makes.
- **Two stub services are still not in `compose.yaml` on purpose.** `allocator` and
  `matchmaker` are still `package main` stubs that print a line and exit, so any
  restart policy would loop them. `session` joined later (`session-migrate`,
  then `session`, on Postgres and Valkey).
- **TLS terminates nowhere in this stack.** The player edge speaks plain HTTP on
  `${GATEWAY_PORT}`; certificates belong to whatever sits in front of it.
- **A rebuild produces a new image ID even when every layer is cached.** Under the
  containerd image store this host uses, `docker build` re-exports the manifest on
  every run, so a tag's ID changes while its contents do not (measured: one unchanged
  gateway build moved from `0ff862...` to `aae859...`). Anything that decides whether
  to recreate a container from the image ID will therefore fire on a rebuild that
  changed nothing, which is why re-running `up.sh` restarts `auth`. It is a reason to
  deploy one service rather than the whole stack on every release.
- **Nothing prunes the registry, and deleting a manifest does not reclaim its blobs.**
  `REGISTRY_STORAGE_DELETE_ENABLED` is set, and a delete should be done by *tag*
  (`DELETE /v2/<name>/manifests/<tag>`, which answers 202). Deleting by digest instead
  removes the manifest and leaves the tag pointing at nothing, which
  `tags/list` shows as `null`. Either way the blobs stay on disk until
  `registry garbage-collect` runs, which nothing here schedules. A repository can also
  stay in `_catalog` with no tags once its manifests are gone, so `_catalog` is not a
  list of what is deployed; `tags/list` is.
- **`release.sh` does not run tests.** COM-12's CI stage does that. A release
  script that also tested would be a second place for the gate to be configured
  differently.

## Releasing

```sh
deploy/scripts/release.sh auth                 # tag = short git SHA of the working tree
deploy/scripts/release.sh gateway 1.4.0        # or an explicit tag
```

It builds the image as `127.0.0.1:5000/otomo-<service>:<tag>`, pushes it, writes
that tag into `deploy/.env`, and recreates the service. For `auth` the recreate
also runs `auth-migrate`, because the two share an image tag and Compose therefore
recreates both.

Rolling back is a re-point, not a rebuild:

```sh
sed -i 's/^OTOMO_AUTH_TAG=.*/OTOMO_AUTH_TAG=<previous sha>/' deploy/.env
cd deploy && docker compose --env-file .env -f compose.yaml up -d auth
```

Tags are immutable and nothing prunes the registry, so the previous image is still
there. Note that a rollback of `auth` needs migrations that are compatible in both
directions; goose does not undo a version on its own.

A tag can be removed deliberately with `DELETE /v2/otomo-<service>/manifests/<tag>`
against `127.0.0.1:5000`, and the space it held is only reclaimed by a
`registry garbage-collect` afterwards. See the trap below before writing anything that
does this automatically.

## What this is not

- **Not COM-8.** No rollback-on-failure, no `/readyz` gate, no Jenkins shared
  pipeline. `release.sh` is the deploy half only, runnable by hand.
- **Not NET-1.** One host, one Compose project. A second host means a Swarm overlay
